# Visual Maps Integration Audit — Phase 3 Smart Hifz Tutor

**Audit date:** 2026-11-13  
**Scope:** Read-only review of the current Visual Maps, Quran navigation, Hifz journey, reader, persistence, and Phase 2 implementation report. No implementation was performed.  
**PDF availability:** A recursive workspace search for `*.pdf` returned no results. The referenced nine-Juz PDFs are therefore not available to inspect in this workspace. Findings about their contents, boundaries, licensing, OCR quality, and import compatibility are **unverified**. Do not infer them from filenames or screenshots.

## 1. Executive summary

Visual Maps already exist as a small, working feature for three hand-authored lessons. They render canonical Quran text from the bundled dataset and offer guided learning, hidden text recall, phrase reveal, ordering, cue matching, and a map-level review schedule. They also share the existing self-assessed Ayah practice flow for independent/final recall.

The current feature is not a scalable map-content system or integrated tutor curriculum yet. The map catalogue and visual cues are compiled into one TypeScript module; the canvas, activities, and scheduling are embedded in one route; lesson content is not linked to Juz, Mushaf page, or a general Quran location resolver; and the due-map recommendation considers only the three bundled maps. PDF import compatibility cannot be determined until the actual source files are placed in the workspace and reviewed.

## 2. Evidence and method

Read the existing Visual Maps data and route, Quran data loader/resolver, Hifz practice and memorization route, app-state store and Supabase sync, reader navigation references, and the Phase 2 Mushaf implementation report. Searched the workspace for PDF files. This was a code and metadata audit only; no tests, build, app launch, device validation, external source checks, or PDF processing were performed.

## 3. Current map inventory

`src/lib/mindMaps.ts` contains three lessons: Al-Fatihah 1:1–7, Al-Baqarah 2:1–5, and Al-Baqarah 2:21–29. Each has a stable string ID, single-Surah start/end, title/subtitle, per-Ayah cue/symbol/color nodes, and colored groups with an Ayah list, symbol, motif, and fixed canvas quadrant. The cues are authored memory associations. The data file explicitly distinguishes these cues from Tafsir.

There is no external map manifest, per-map file, multi-Surah reference, word-range annotation, data version, content checksum, review state, author/reviewer field, source citation, or license field in the map schema. The catalog is small today, but bundling all future lessons in the same module would eagerly ship them to every client.

## 4. Quran text and meaning sources

Arabic text comes from the existing bundled Quran data through `text()`/`words()`; the map schema does not store or rewrite verse text. Quran text is split into visual rows at runtime (normally 12 words, five for Al-Fatihah 1:7), rather than using editor-authored phrase boundaries. English and Urdu translations and Arabic Tafsir are loaded from separate Quran data sets; the view labels their sources and distinguishes Tafsir from the cues. This is a useful integrity boundary to preserve.

The current cue/group metadata itself has no recorded Tafsir citation or review provenance. Treat it as a mnemonic label, not an authoritative interpretation. No claim is made here that every cue is scholarly reviewed.

## 5. Existing visual and learning experience

The route (`src/app/mind-maps/page.tsx`) provides a fixed 1600×1000 SVG-connected map with a central lesson hub, four quadrant layouts, colored trunks, node rows, small inline motifs, zoom, fit, fullscreen, and print/browser-PDF. The design is illustrative in a limited, code-drawn sense; current symbols are Unicode/emoji and inline geometric motifs, not an imported illustrated map asset or PDF page reproduction. The stage horizontally scrolls on narrow screens rather than reflowing the map topology.

The seven displayed stages cover whole-map viewing; meaning study; progressively revealed Quran phrases; hidden-Ayah recall; map-hidden independent recall; Ayah sequence reconstruction; and a final memorization test. Available activities include cue-to-Ayah matching and a shuffled Ayah-order exercise. A selected node can show its Quran text, translations, Tafsir, audio, and recitation practice. Map recall hides the branch text across the map; it does not provide an authored independent branch-removal/reconstruction editor.

Phrase chunks are generated by word count, not authored semantic phrase annotations. The “recite” button opens the existing Practice experience, where the learner reveals the Ayah and self-marks recall. No objective speech recognition is implied by this audit.

## 6. Existing integration with Hifz

There are two distinct progress paths:

- **Map-level state:** `mapProgress[map.id]` stores map status, due time, last review, repetition/interval, quiz counters, current stage/selected Ayah, and optional assessment streak fields. The map route schedules map ratings and records map quiz results here.
- **Ayah-level state:** `Practice` calls `applyResults()` for its session. Map independent/final recall uses `kind: "assessment"`; it calls the same per-Ayah Hifz update path as other assessments and persists learner self-ratings. Meaning/order completion alone does not create or update Ayah memorization records.

The map assessment is learner self-report, not verified recitation. Preserve this distinction in future dashboards and tutor decisions. Do not let cue matching or order correctness imply that the corresponding Ayahs have been recited correctly.

## 7. Current Hifz journey connection

The Memorize page links to Visual Maps. It can recommend a due visual map after regular due Ayahs and weak Ayahs, but only from the hardcoded catalog and only when a map progress entry exists and is overdue. It opens `/mind-maps?map=<id>`. There is no map selection/configuration in the study plan, no coverage rule connecting maps with a chosen Surah/Juz, and no “start map for this selected Quran range” action.

## 8. Quran location and Mushaf integration

The app already has a shared location resolver and a `LocationNavigator` for Surah, Ayah, Juz, Hizb, quarter, and page. The Mushaf accepts exact Surah/Ayah routes. The Visual Maps feature does not use this shared resolver: map locations are single-Surah `{surah, from, to}` fields. There is no map page/Juz/Hizb/quarter index, no cross-Surah span, and no navigation handoff from a selected map node into a Mushaf focused Ayah. This can be added as a reference link while retaining current location IDs and existing 604-page reader data.

Phase 2's report states the reader retains the existing layout and routes, but its reconstructed page/line layout differs from the cited KFGQPC V2 coordinates, and Android visual/device behavior remains unverified. A Visual Maps integration should target canonical Ayah IDs and the existing resolver, not assume publisher-exact page artwork.

## 9. Persistence, migration, and synchronization

App state remains schema `v: 1`, with map progress in its own top-level `mapProgress` field. The store hydrates new optional fields from defaults, local storage keeps the state, guest-to-account merge combines map progress by latest `last`, and Supabase sync stores the whole `AppState` JSON snapshot. Existing map progress is thus separate from `mem`/`weak` and participates in current whole-state syncing.

For added fields, retain stable IDs (`al-fatihah`, `al-baqarah-1-5`, `al-baqarah-21-29`) and use backward-compatible defaults or an explicit safe migration. Avoid replacing the entire `mapProgress`, `mem`, `weak`, history, or journey state during content updates. Avoid renaming existing map IDs without alias migration. Test old v1 saves and guest/account merge before any future migration.

## 10. Scalability and performance

Current risks if expanded to hundreds of maps:

- All map lesson definitions live in one statically imported module.
- The page loads whole English/Urdu translation arrays and the full Tafsir array at mount, even though a lesson shows one selected Ayah at a time. `loadSet` caches data after retrieval, but first visit can still fetch large sets.
- The visual canvas creates row elements from the word data on each map render and is fixed-size, with horizontal scrolling on small displays.
- The map catalog/list and due-map selection scan the same complete in-memory array.

For scale, use a small versioned manifest/index for catalog, stable IDs, ranges, and lookup; load the chosen map document on demand; fetch or read translations/Tafsir only as needed if the existing API supports it; and include a map content version/review/source record. Keep Quran text external to map documents and resolve each map reference to canonical Ayah IDs. Preserve selected-map/offline support through an explicit service-worker caching policy for map documents instead of precaching an entire nine-Juz corpus by default.

## 11. Reuse candidates

| Existing component/API | Reuse | Current limitation |

| `MindMapLesson` / `MIND_MAPS` | Preserve lesson IDs and migrate records | Type is too small for multi-Surah references, phrase data, provenance, or versioning |

| `text()`, `words()`, `loadSet()` | Canonical Arabic and existing translation/Tafsir sets | Translation and Tafsir currently load as whole sets |

| `Practice` / `applyResults()` | Genuine per-Ayah self-rated recall and Hifz SRS | Learner self-assessment; should not absorb map-concept quiz scores |
| `mapProgress` | Map-level status and due review state | Current record tracks one map session summary, not branch/concept mastery |
| `MindMapCanvas` | Current standalone presentation | Private to the route, fixed geometry, not exported for tutor embedding |
| Memorize daily journey | Surface due maps | Only three static maps and only existing overdue records |

## 12. Suggested integration architecture (recommendation, not implementation)

Separate map **content**, **presentation**, **activities**, and **progress**:

1. A versioned map catalog with stable map IDs, canonical Ayah ranges, display metadata, reviewer/source/license provenance, and lazy document paths.
2. A shared viewer component that accepts a loaded map and selection/visibility callbacks, usable from standalone Visual Maps and a tutor flow.
3. Activity runners for phrase reveal, visual recall, cue matching, branch ordering/reconstruction, and final Ayah recall, each with explicit answer/complete outcomes.
4. Map/concept activity scores stored only in map progress. Route actual recitation/self-rated Ayah results through existing `Practice` and `applyResults()`.
5. Integration through the existing Quran location resolver to open the correct Surah/Ayah and to start a selected range without recording automatically.
6. A tutor planner that combines map due state with existing Ayah due/weak state, respects current Hifz history, and does not count the same work twice.

## 14. Mobile, offline, print, and accessibility

The page includes touch-friendly controls, zoom, fullscreen, and print. The fixed wide canvas may require pan/zoom on phones and has no observed structural reflow. Existing app shell navigation exposes Visual Maps. Android behavior was not independently verified in this audit. The Phase 2 report likewise says Android device/emulator checks were not performed.

Maps currently ship as application code. If converted to separate JSON, ensure the service worker caches a requested map intentionally and can reopen it offline. Before a larger rollout, check keyboard traversal, visible focus, screen-reader labels for every branch, zoom limits, Arabic shaping, portrait/landscape, print breaks, and Android WebView fullscreen/back behavior.
