## 5. Android build workflow

**Can GitHub's Windows runners reproduce the existing build? Yes, with environment preparation.** The workflow runs `scripts/build-android.ps1` itself, unmodified, in Windows PowerShell, just like `npm run build:android`. These steps make the runner look like your PC:

1. `git config core.autocrlf false` before checkout. Windows runners convert LF to CRLF by default, which would change the bytes of `quran.json` and every frontend file.
2. JDK 17 on `PATH` (the script derives `JAVA_HOME` from `java`).
3. Android SDK platform 36 installed. A private `LOCALAPPDATA`, used only for the build step, points `%LOCALAPPDATA%\Android\Sdk` at the runner's SDK.
4. Gradle 8.14.3 downloaded from services.gradle.org, its SHA-256 checked against a pinned value and Gradle's published checksum, then unpacked into `%USERPROFILE%\.gradle\wrapper\dists\gradle-8.14.3-bin\…`, where the script looks for it.
5. One online warm-up `assembleDebug` of the native shell, because the script runs Gradle with `--offline`. Its output is deleted before the real build.

The script then does what it does locally: removes stale output, builds the export with `BUILD_ANDROID=1`, checks the required pages, stamps the build ID (`build-info.mjs stamp`), copies the export into `android/app/src/main/assets/public` (`_next` → `next`), runs `assembleDebug` with an increasing `versionCode`, and verifies the APK.

## 8. Android signing safety status

**Status: the CI APK is NOT safe to install over your existing app.**

What I found:

- `android/app/build.gradle` has no `signingConfigs`. `assembleDebug` therefore signs with the Android debug keystore of whichever machine builds it. On your PC that is `%USERPROFILE%\.android\debug.keystore`. That file is not, and should not be, in the repository.
- A GitHub runner creates its own fresh debug keystore. The CI APK's certificate is `CN=Android Debug, O=Android, C=US`, SHA-256 `48:fe:b1:bf:f5:35:cf:0a:9b:c9:97:ef:2e:ee:4f:e3:57:bd:fd:78:e3:9d:15:56:97:e7:71:26:26:c6:85:e9` (from run 44040216902). Every debug key has the same name (DN), so only the SHA-256 shows which key it is. Runners can generate a new key each run, so this digest can change between runs.
- Android only installs an update when the certificate matches. A CI APK will fail with "App not installed"/signature conflict on your phone. **Do not uninstall the existing app or clear its data to get around this: that would delete your saved memorization progress.**
- The package ID `com.hifzcompanion` is unchanged and checked.
- versionCode = minutes since 2024-01-01 UTC at build time (the script's rule, unchanged). It always rises over time, so a later build gets a higher code (1513901 for the run above).

What was not done, on purpose: no keystore, password or signing secret was created, uploaded or committed, and the signing certificate was not changed.

To check which key signed your installed app, run this on your PC, against an APK you previously installed:

```
"%LOCALAPPDATA%\Android\Sdk\build-tools\36.0.0\apksigner.bat" verify --print-certs "C:\path\to\Hifz-Journey-<buildId>-debug.apk"
```

### Enabling matching signatures later (only with your approval)

Option A: reuse your PC's debug key (keeps in-place updates working for the current install):

1. On your PC, base64-encode the keystore: `[Convert]::ToBase64String([IO.File]::ReadAllBytes("$env:USERPROFILE\.android\debug.keystore")) | Set-Content debug.keystore.b64`. Keep this file private and delete it afterwards.
2. GitHub → repository **Settings → Secrets and variables → Actions → New repository secret**, name `HIFZ_DEBUG_KEYSTORE_B64`, and paste the content.
3. Add a step before the build that, when the secret exists, writes it to `%USERPROFILE%\.android\debug.keystore` on the runner. Then compare the printed certificate SHA-256 with your local one, and only then relabel the artifact as update-capable.

Option B: create a proper release key and `signingConfigs.release` read from secrets (`HIFZ_KEYSTORE_B64`, `HIFZ_KEYSTORE_PASSWORD`, `HIFZ_KEY_ALIAS`, `HIFZ_KEY_PASSWORD`). This is the right path for the Play Store, but an app signed with a new key cannot update the current debug-signed install. You would need to export a backup from the app first.

In both cases, secrets are never echoed to the log, are not available to pull requests from forks, and the keystore file stays out of git (`*.jks`, `*.keystore` are already ignored).
